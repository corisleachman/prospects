Start with a useful outcome.

Build your own new business engine

Build your own connected tools.

A CRM-like page is one example. The bigger idea is connecting the systems you already use, then making them work in a way that suits you.

That might be a prospects dashboard, a view of your team's capacity, or a page that brings jobs and follow-ups together. Your CRM, Synergist or Monday.com could sit behind it. Start with what you want to achieve, then let Claude or Codex help you work out what needs connecting.

The principle

Say what you want in plain English.

Let the AI ask you what it needs to know. Choose the accounts your build actually needs. Connect the systems, then test one useful thing at a time.

My example: new business

A page that brings prospects, saved messages and follow-ups into one place, with email connected so I can act from the same view.

Your example: resourcing

A page that brings jobs and team availability into view, using information from your existing resourcing software, where its integration options allow it.

Start with the end goal

Describe what you want.

Talk to Claude or Codex as you would to someone helping you solve a problem. Explain what you want to see and what you want to be able to do.

Explain the job

Who's using it? What takes too much effort today? What should become easier? Describe a real situation, rather than starting with a list of features.

Name your existing systems

Tell it where the information already lives, whether that's a CRM, Synergist, Monday.com, Gmail or a spreadsheet. Say which system should remain the main record.

Let it ask questions

Ask it to clarify anything it needs before building. It should check who can access the tool, what it can change and how your systems can connect.

Decide what done looks like

Pick one useful outcome for the first version. A working contact view or a weekly capacity view is enough to start. Everything else can wait.

A starting prompt

I want to build a simple tool that helps me [describe the outcome]. Right now, I use [name the systems] and the problem is [explain what makes the job difficult]. The people using this will be [who]. For the first version, I want to see [information] and be able to [actions]. Keep [existing system] as the main record. Ask me before anything sends a message or changes live data. Ask me the questions you need answered before you build. Then propose the smallest useful version, explain which accounts or connections it needs, and walk me through the setup in plain English. Use dummy data first. Done means [one clear outcome I can test].
Example: a CRM-like page

“I want a page that shows my prospects, lets me filter them, saves message templates and helps me keep track of follow-ups. My contacts are currently in a spreadsheet. I want to review each message before it sends. Ask me what you need to know before building.”

Example: a resourcing view

“I want a clear weekly view of live jobs and who's available, using the data we already keep in Synergist or Monday.com. Start with a read-only view. Find out what connections our account supports before suggesting anything that writes back.”

03 / 08Next: connect and build →
Make one useful thing work

Connect & build.

Let the AI guide the setup for your specific idea. Every connection should have a clear purpose and a clear boundary.

01

Agree the first version

Have it explain the page, the systems behind it and what information moves between them. Confirm what can only be read and what can be changed. Keep the first version small.

02

Set up the right accounts

Use the account list as a guide. Ask the AI to take you through the sign-ups and explain unfamiliar terms as they appear. Keep ownership of the accounts and access.

03

Connect with permission

Use an approved sign-in or connector where available. If a service requires a token, give it only the access it needs and use a secure credential setup. Keep secret tokens out of chat, screenshots, browser code and GitHub.

For Synergist, Monday.com or a CRM, first check the integration options your account actually supports. If there's no suitable live connection, start with an export or a smaller version.

04

Build with dummy data

Ask it to create a preview. Check the layout and try the main task with sample records. Save a working version in GitHub before the next change.

05

Test the whole job

Does the right information appear? Does a saved change reach the intended system? Can the right people access it, and can someone without permission get in? For email, test to your own address and check that it arrives.

06

Publish, then improve

Ask the AI to guide deployment to the host you've chosen. A public web address isn't an access control. Check sign-in and data permissions before connecting real records, then improve one thing at a time.

If you're connecting Gmail

Ask your assistant to guide the current Google Cloud setup for the app it's building. You'll usually need a project with the Gmail API enabled, an OAuth consent setup and an OAuth client configured for your app's actual URLs.

Use the minimum permissions needed. Test with your own account first. A Google Client ID is public; a client secret or access token isn't. Test-user settings, app verification and redirect requirements depend on the integration, so get the assistant to check the current instructions rather than blindly copying someone else's settings.

Understand any permission or unverified-app warning before approving it. Check that the app and requested access are the ones you intended.

Google's Gmail authorisation guide ↗
If you're using Resend

Ask the AI to walk you through sender/domain setup and a test email. Store the secret API key on the server, for example in your app host's environment settings. Your page asks the server to send the email; it never exposes the key in the browser.

Keep sending behind the right access checks, and ask for confirmation before real messages go out.

When it breaks, and it will

How to Get Unstuck.

You don't need to diagnose everything yourself. Give the AI something concrete to work with.

01

Paste the error back in

Copy the whole message, red text and all. It's usually everything the AI needs.

02

Show, don't describe

If something looks wrong, give it a screenshot rather than an explanation.

03

Ask what it just did

Get it to explain in plain English. You learn the stack as you go.

04

One change at a time

Small steps, saved in GitHub, so you can always roll back.

Remove passwords, secret tokens and private client information from errors and screenshots before sharing them.

A prompt for a broken step

I expected [what should happen], but [what actually happened]. Here's the full error or a screenshot, with private information removed. Explain what's going wrong in plain English. Propose one small fix, tell me how to test it, and save the working version before making further changes.

Keep control as you build

Security & the Wild West.

Enthusiasm can move much faster than access control, privacy and maintenance.

Client data

Use dummy data while experimenting and demonstrating.

Access

Know which systems and information the tool can reach.

Storage

Understand where the data lives and who controls it.

Maintenance

Know when the build has outgrown a personal experiment.

Public keys can sit in your code. Secret tokens never do.

Keep tokens small in scope, give them an expiry, and rotate them after use. A public key still needs proper access rules behind it.

Which credentials can be public?

A Google OAuth Client ID and a Supabase publishable or legacy anon key are designed for client-side use. They identify the app or project; they don't replace authentication or database access rules.

GitHub access tokens, Resend API keys, Supabase secret/service-role keys and OAuth client secrets are credentials. Keep them in secure server-side configuration, never in the page or repository.

How do I keep access under control?
  • Prefer an approved sign-in or connector over sharing raw credentials.
  • Limit access to the account, repository or actions the job needs.
  • Protect private data with real authentication and permission checks, not a hidden URL.
  • Revoke one-off access when you're finished. Rotate a secret immediately if it becomes exposed.
When does an experiment need more support?

When colleagues depend on it, it handles client information, or it can change important records, give it an owner and a maintenance plan. Agree how to back up data, recover from a failure and review access. Bring in technical help where you need it.

The honest bit

The Caveats.

There's real value in building your own tools. These are the things to keep in view while you do it.

01

Security

Public keys can sit in your code. Secret tokens never do. Keep tokens small in scope, give them an expiry, and rotate them after use.

Read the security section →
02

Complexity

You will go down a rabbit hole. The good news is that every model update and new service takes another layer of it away.

Some connections still take work. Ask the AI to explain the simplest route, and step back if the build starts growing beyond the problem you set out to solve.

03

Knowing when to stop

It's very easy to keep tinkering. Decide what done looks like before you start.

When the first version does the job you agreed, use it. Keep extra ideas in a separate list rather than turning every thought into another feature.

Useful beats endlessly unfinished.

Pick a real job, make a small version work, and learn from using it.
